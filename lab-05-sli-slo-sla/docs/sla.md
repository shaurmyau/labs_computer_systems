# Проект соглашения об уровне обслуживания (SLA) для OrderFlow

**Статус документа:** учебный проект, не является действующим юридическим договором.

## 1. Стороны

- **Поставщик:** учебная команда сопровождения OrderFlow.
- **Потребитель:** организация-заказчик, использующая сервис для приёма онлайн-заказов.

Реквизиты и уполномоченные представители заполняются сторонами при заключении реального соглашения.

## 2. Предмет соглашения

Поставщик обеспечивает доступность пользовательского API OrderFlow, приемлемое время ответа и своевременную сохранность подтверждённых заказов. Соглашение распространяется на API каталога, создание заказа и получение статуса заказа в пределах контролируемой инфраструктуры поставщика.

## 3. Показатели и договорные уровни

| SLI | Метод измерения | Обязательство SLA |
|---|---|---|
| Доля успешных eligible-запросов | Успешные HTTP 2xx/3xx к eligible-запросам за календарный месяц | ≥ 99,90% |
| p95 времени ответа | 95-й процентиль server-side API latency за календарный месяц | ≤ 700 мс |
| Доступность подтверждённого заказа для чтения | Доля заказов, доступных не позднее 60 с после подтверждения | ≥ 99,90% |

Определения eligible-запросов, исключения 4xx и служебных маршрутов, источники данных и точные формулы приведены в документе SLI/SLO. При расхождении между dashboard и журналом транзакций приоритет имеет согласованный источник данных и процедура сверки.

## 4. Период измерения и действия

- Период измерения — календарный месяц, UTC.
- Соглашение вступает в силу с даты письменного принятия сторонами.
- Поставщик формирует отчёт не позднее пятого рабочего дня следующего месяца.
- Пересмотр проводится ежеквартально или после существенного изменения архитектуры, нагрузки либо критичных бизнес-функций.
- Изменения порогов оформляются согласованной редакцией документа.

## 5. Мониторинг и отчётность

Поставщик использует Prometheus, журналирование API и контрольные проверки доступности заказов. Отчёт содержит значения SLI, период измерения, объём выборки, исключённые события, инциденты и расчёт компенсации при наличии основания.

## 6. Эскалация

1. При прогнозируемом нарушении SLI дежурный инженер начинает диагностику и регистрирует инцидент.
2. При недоступности критической функции уведомляется контакт заказчика.
3. Для инцидента уровня критичности P1 первичное уведомление направляется не позднее 30 минут после подтверждения инцидента.
4. Поставщик предоставляет предварительное описание причины и мер восстановления, затем итоговый отчёт с корректирующими действиями.

## 7. Компенсации

При нарушении месячной доступности по SLI 1 потребитель вправе запросить сервисный кредит от ежемесячной платы за затронутую услугу:

| Фактическая доступность | Сервисный кредит |
|---|---:|
| 99,00%–менее 99,90% | 10% |
| Менее 99,00% | 25% |
| 99,90% и выше | 0% |

Общий размер кредита не превышает 25% ежемесячной платы за соответствующую услугу. Запрос подаётся в течение 30 календарных дней после получения отчёта. В реальном соглашении формулу необходимо согласовать с юридической и финансовой службами.

Нарушение SLI 2 или SLI 3 запускает обязательное расследование и план корректирующих действий; дополнительные финансовые санкции по этим метрикам должны быть отдельно согласованы сторонами и здесь не предполагаются автоматически.

## 8. Исключения

SLA не применяется к периоду, вызванному:

- заранее объявленными плановыми работами длительностью не более четырёх часов в месяц, уведомление о которых направлено не менее чем за 72 часа;
- форс-мажором, подтверждённым в установленном порядке;
- отказом оборудования, сети или программного обеспечения заказчика за пределами зоны ответственности поставщика;
- действиями заказчика, нарушающими опубликованные требования API или правила безопасной эксплуатации.

Ошибки и отказы внутри контролируемой инфраструктуры поставщика не исключаются только на основании того, что они вызваны внутренней зависимостью.

## 9. Обязанности сторон

Поставщик поддерживает мониторинг, резервное копирование, процесс управления инцидентами и отчётность. Потребитель предоставляет актуальные контакты, сообщает о наблюдаемых сбоях и использует сервис согласно документации.

## 10. Принятие

В рабочем документе должны быть добавлены дата вступления в силу, реквизиты сторон, контактные лица и подписи уполномоченных представителей.
