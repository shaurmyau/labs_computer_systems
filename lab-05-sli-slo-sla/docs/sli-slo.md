# Модель SLI и SLO для OrderFlow

Период оценки для всех целей — скользящие 30 календарных дней. Для расчётных примеров месяц условно принимается равным 30 дням. Источники — Prometheus и журналы API/проверки хранения заказов.

## SLI 1. Доля успешных пользовательских запросов

**Что измеряет:** долю валидных пользовательских API-запросов, завершившихся ответом HTTP 2xx или 3xx.

Формула:

~~~text
SLI_success = N(HTTP 2xx или 3xx) / N(все eligible-запросы) × 100%
~~~

Eligible-запросы — все пользовательские запросы, кроме заведомо некорректных ответов 4xx и технических маршрутов /health и /metrics. Таймауты, 5xx и недоступность балансировщика считаются неуспешными запросами.

| Параметр | Значение |
|---|---|
| Источник | Prometheus, счётчик http_requests_total |
| Единица | % |
| SLO | не менее 99,95% за 30 дней |
| Допустимое отклонение / сигнал анализа | менее 99,97% в текущем окне или расход более 50% бюджета ошибок |
| SLA | не менее 99,90% за календарный месяц |

## SLI 2. Время ответа пользовательского API

**Что измеряет:** 95-й процентиль серверного времени обработки eligible-запросов. Время измеряется от поступления запроса на API до отправки ответа, без времени рендеринга клиентского интерфейса.

Формула:

~~~text
SLI_latency = percentile_95(request_duration_seconds)
~~~

| Параметр | Значение |
|---|---|
| Источник | Prometheus histogram http_request_duration_seconds |
| Единица | миллисекунды |
| SLO | p95 не более 400 мс за 30 дней |
| Допустимое отклонение / сигнал анализа | p95 выше 350 мс в двух последовательных суточных окнах |
| SLA | p95 не более 700 мс за календарный месяц |

Для агрегирования histogram используется объединение buckets по всем экземплярам API с сохранением label le. Клиентские 4xx и служебные маршруты исключаются по той же политике, что и для SLI 1.

## SLI 3. Своевременная доступность подтверждённых заказов

**Что измеряет:** долю принятых API заказов, которые успешно записаны и становятся доступны для чтения не позднее 60 секунд после подтверждения приёма.

Формула:

~~~text
SLI_order_integrity = N(заказы, доступные для чтения за 60 с) / N(принятые заказы) × 100%
~~~

| Параметр | Значение |
|---|---|
| Источник | Счётчики orders_accepted_total и orders_verified_within_60s_total, журнал транзакций |
| Единица | % |
| SLO | не менее 99,99% за 30 дней |
| Допустимое отклонение / сигнал анализа | любое подтверждённое расхождение; автоматическое расследование при снижении ниже 99,995% |
| SLA | не менее 99,90% за календарный месяц |

Этот SLI отражает критическую бизнес-ценность: клиент не должен получить подтверждение заказа, который затем невозможно найти. Повторные технические события для одного заказа должны дедуплицироваться по order_id.

## Сводная таблица SLI / SLO / SLA

| SLI | SLO | SLA | Почему SLO строже |
|---|---|---|---|
| Доля успешных запросов | ≥ 99,95% за 30 дней | ≥ 99,90% за месяц | Внутренний запас 0,05 п.п. позволяет реагировать до нарушения договорного уровня |
| p95 времени ответа | ≤ 400 мс | ≤ 700 мс | Запас 300 мс покрывает пики нагрузки и вариацию внешней сети |
| Заказы доступны для чтения за 60 с | ≥ 99,99% за 30 дней | ≥ 99,90% | Данные критичны для бизнеса; высокий внутренний порог стимулирует раннее обнаружение проблем |

## Обоснование

SLO — инженерная внутренняя цель и должна оставлять запас относительно обязательства SLA. Если SLO совпадает с SLA, у команды нет эксплуатационного запаса на обнаружение, диагностику и исправление тенденции до нарушения договора. Для доступности разница 99,95% против 99,90% соответствует примерно 21,6 минутам и 43,2 минутам допустимого недоступного времени соответственно за условные 30 суток. Для задержки внутренний порог 400 мс заметно ниже договорного предела 700 мс. Для сохранности заказов SLO 99,99% задаёт более высокий защитный уровень, чем SLA 99,90%.
