# Модель SLI и SLO для Sirius EDA

Период оценки для целей — скользящие 30 календарных дней. Для расчётных примеров месяц условно принимается равным 30 дням. Источники данных — метрики HTTP API, журналы приложения, PostgreSQL и события RabbitMQ/фоновых обработчиков.

## SLI 1. Доля успешных пользовательских HTTP-запросов

**Что измеряет:** долю валидных пользовательских запросов к API, завершившихся ответом HTTP 2xx или 3xx.

Формула:

~~~text
SLI_success = N(HTTP 2xx или 3xx) / N(все eligible-запросы) × 100%
~~~

Eligible-запросы — пользовательские запросы, исключая заведомо некорректные 4xx и технические маршруты health-check/metrics. Таймауты, 5xx и недоступность API считаются неуспешными запросами.

| Параметр | Значение |
|---|---|
| Источник | HTTP-метрики FastAPI и журналы запросов |
| Единица | % |
| SLO | не менее 99,95% за 30 дней |
| Сигнал анализа | менее 99,97% в текущем окне или расход более 50% бюджета ошибок |
| SLA | не менее 99,90% за календарный месяц |

## SLI 2. Время ответа пользовательского API

**Что измеряет:** 95-й процентиль серверного времени обработки eligible-запросов к меню, балансу и операциям заказа. Время измеряется на стороне API, без времени рендеринга клиентского интерфейса и без длительности всей асинхронной обработки.

Формула:

~~~text
SLI_latency = percentile_95(request_duration_seconds)
~~~

| Параметр | Значение |
|---|---|
| Источник | HTTP histogram FastAPI |
| Единица | миллисекунды |
| SLO | p95 не более 400 мс за 30 дней |
| Сигнал анализа | p95 выше 350 мс в двух последовательных суточных окнах |
| SLA | p95 не более 700 мс за календарный месяц |

Для агрегирования histogram объединяются buckets всех экземпляров API с сохранением границы bucket. Клиентские 4xx и служебные маршруты исключаются по той же политике, что и для SLI 1.

## SLI 3. Успешное завершение асинхронной обработки заказа

**Что измеряет:** долю подтверждённых событий заказа, для которых за установленное время получен ожидаемый результат: обработка кухней и дальнейшее назначение доставки либо корректно зарегистрированная Saga-компенсация.

Формула:

~~~text
SLI_order_flow = N(заказы с подтверждённым результатом за 5 мин) / N(принятые к обработке заказы) × 100%
~~~

| Параметр | Значение |
|---|---|
| Источник | журналы событий, RabbitMQ, статусы заказов PostgreSQL, журналы workers/Saga |
| Единица | % |
| SLO | не менее 99,90% за 30 дней |
| Сигнал анализа | любое подтверждённое потерянное событие; автоматическое расследование при снижении ниже 99,95% |
| SLA | не менее 99,50% за календарный месяц |

Повторные доставки одного события должны учитываться по идентификатору события/заказа, а не как отдельные успешные операции. Успешный HTTP-ответ на создание заказа не считается подтверждением завершения асинхронного процесса.

## Сводная таблица SLI / SLO / SLA

| SLI | SLO | SLA | Почему SLO строже |
|---|---|---|---|
| Доля успешных HTTP-запросов | ≥ 99,95% за 30 дней | ≥ 99,90% за месяц | Внутренний запас 0,05 п.п. позволяет реагировать до нарушения договорного уровня |
| p95 времени ответа API | ≤ 400 мс | ≤ 700 мс | Запас 300 мс покрывает пики нагрузки и вариацию инфраструктуры |
| Асинхронный результат заказа за 5 мин | ≥ 99,90% | ≥ 99,50% | Внутренняя цель стимулирует обнаруживать задержки и потери событий до нарушения SLA |

## Обоснование

SLO — внутренняя инженерная цель, поэтому она должна оставлять запас относительно обязательства SLA. Если SLO совпадает с SLA, у команды не остаётся эксплуатационного запаса на обнаружение, диагностику и исправление тенденции до нарушения договорного уровня.

Для Sirius EDA важно измерять два разных аспекта: быстрый ответ API и завершение асинхронного бизнес-процесса. API может принять запрос, но последующая обработка события в RabbitMQ, кухонном или доставочном worker может задержаться. Поэтому эти показатели нельзя объединять в одну метрику. Все значения являются учебными целями и требуют проверки на реальной телеметрии.
