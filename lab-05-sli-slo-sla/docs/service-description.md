# Описание системы Sirius EDA

## Назначение

Sirius EDA — информационная система заказа питания в столовой. Она позволяет пользователям просматривать меню, пополнять баланс, создавать и оплачивать заказы, а также получать сведения о состоянии заказа и доставке.

## Пользователи и роли

- **Студент / пользователь** — просматривает меню, управляет балансом, создаёт заказ и отслеживает его состояние.
- **Повар** — получает заказы на приготовление и обновляет состояние кухонного этапа.
- **Курьер** — получает назначение на доставку и передаёт обновления по доставке.
- **Администратор** — управляет меню, пользователями и операционными настройками.

## Архитектурная модель

В качестве предметной модели рассматриваются следующие компоненты:

- FastAPI — HTTP API и бизнес-операции;
- PostgreSQL — хранение пользователей, меню, балансов и заказов;
- RabbitMQ — передача событий между API и асинхронными обработчиками;
- фоновые обработчики кухни и доставки — выполнение этапов заказа;
- Saga — координация компенсационных действий при ошибках процесса.

Создание заказа и последующая обработка — разные этапы. Успешный HTTP-ответ сам по себе не доказывает, что событие обработано кухней и заказ завершил дальнейший жизненный цикл.

## Критические бизнес-функции

1. **Доступность меню.** Пользователь получает актуальные позиции и цены.
2. **Создание и оплата заказа.** Заказ сохраняется, баланс обрабатывается согласно бизнес-правилам, операция получает однозначный идентификатор.
3. **Асинхронная обработка.** Событие об оплате передаётся обработчикам кухни и доставки; ошибки приводят к согласованной компенсации, а не к потере заказа или средств.

## Характер нагрузки

Базовая нагрузка распределена в течение учебного дня. Пики ожидаются перед обеденным временем и в начале вечернего периода. Для расчётов используются пользовательские HTTP-запросы и события жизненного цикла заказа. Технические маршруты health-check и metrics исключаются из пользовательских SLI.

## Границы измерения

- HTTP-доступность и задержка измеряются на входе FastAPI API.
- Целостность заказа проверяется по согласованному состоянию PostgreSQL.
- Асинхронная обработка измеряется от публикации события до подтверждённого результата обработчика кухни/доставки либо зарегистрированной компенсации Saga.

Ошибки клиента 4xx не включаются в знаменатель доступности пользовательских запросов, если они вызваны некорректным вводом. Серверные 5xx, timeout, недоступность API и потеря обязательного события учитываются как неуспешные операции.
