# Индивидуальное задание: метрики и триггер

## Фиксация метрик

Открой Monitoring → Latest data, выбери Zabbix-local и зафиксируй значения с отметкой времени. Выбирай последние значения, относящиеся к одному интервалу наблюдения.

| Метрика | Что записать | Пример учебного значения* |
|---|---|---:|
| CPU utilization | Загрузка процессора, % | 12,4% |
| Memory utilization | Использование памяти, % | 63,0% |
| Disk space | Свободный объём и общий объём либо процент использования | 48 ГБ свободно из 120 ГБ (40%) |
| Network traffic | Входящий и исходящий трафик, байт/с | RX 14 КБ/с, TX 8 КБ/с |

* Значения демонстрационные. Они не являются результатом измерения твоего сервера и должны быть заменены фактическими показаниями Zabbix.

Зафиксируй имя узла, дату и время наблюдения, интервал опроса item, имя и версию шаблона, состояние доступности агента.

## Настройка триггера

| Поле | Значение |
|---|---|
| Name | CPU load > 80% for 5m |
| Severity | Warning |
| Item | system.cpu.util |
| Function | avg |
| Period | 5m |
| Operator | > |
| Threshold | 80 |

Выражение:

~~~text
avg(/Zabbix-local/system.cpu.util,5m)>80
~~~

Если шаблон использует иной ключ CPU item, подставь ключ фактического item. Не создавай триггер по несуществующему item.

## Проверка

1. Убедись, что Latest data получает свежие значения.
2. В Configuration → Hosts проверь, что Zabbix-local включён и агент доступен.
3. В Configuration → Hosts → Triggers проверь выражение, важность Warning и статус Enabled.
4. На учебной машине при согласованном тесте можно создать контролируемую CPU-нагрузку на пять минут и проверить появление Problem. Не выполняй нагрузочный тест на рабочем сервере.
5. После теста прекрати генерацию нагрузки и проверь переход проблемы в Resolved.

## Вывод

Установка подтверждена, если Server, Agent, Nginx, PHP-FPM и MySQL активны, Frontend доступен, Latest data содержит свежие метрики узла, а триггер сохранён с требуемым выражением. В отчёте отделяй факт проверки от ожидаемого результата и демонстрационных значений.
