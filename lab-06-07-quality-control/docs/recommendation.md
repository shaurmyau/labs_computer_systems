# Рекомендация по улучшению качества OrderFlow

## Рекомендация

Внедрить идемпотентное создание заказа: принимать обязательный Idempotency-Key для POST /api/orders, сохранять ключ вместе с customer_id и результатом операции, обеспечивать уникальное ограничение на пару (customer_id, idempotency_key). При повторе с тем же ключом API возвращает ранее сформированный order_id и исходный результат, а не запускает создание заказа повторно.

## Основание

Рекомендация адресует BUG-001 — дублирование заказов при повторной отправке после timeout. Дефект может привести к двойному резервированию товара, повторной обработке заказа и дополнительной нагрузке на поддержку. Также он напрямую затрагивает критичную функцию OrderFlow — оформление заказа.

## Тип действия

**Корректирующее действие.** Дефект уже выявлен в ходе тестирования, поэтому мера устраняет установленную причину повторного создания заказа. Дополнительное предупреждающее действие — требование идемпотентности для всех новых денежных и заказных API-операций — следует включить в архитектурные стандарты.

## План выполнения

| Поле | Значение |
|---|---|
| Ответственный | Backend team lead |
| Исполнители | Backend-разработчик и QA-инженер |
| Срок | 7 календарных дней от утверждения рекомендации (условно) |
| Приоритет | P1 / High |
| Результат | Idempotency-Key, уникальный индекс, сохранение результата, интеграционные тесты |

## Проверка эффективности

1. Отправить один и тот же POST с одинаковым Idempotency-Key последовательно дважды.
2. Повторить тест с параллельными запросами.
3. Смоделировать timeout клиента после фиксации операции в БД и отправить запрос повторно.
4. Проверить, что все ответы содержат один и тот же order_id, а в БД остаётся одна запись.
5. Проверить конфликт, если тот же ключ используется с другим payload: API должен вернуть 409 Conflict или согласованный эквивалент и записать событие аудита.
6. Добавить регрессионные проверки в CI.

Критерий успеха: 100% повторов с одним ключом не создают новую запись; тесты на конкурентные запросы проходят; количество дублей после релиза равно нулю. Дополнительный мониторинговый показатель — количество попыток повторного создания / число подтверждённых дублей, с alert при любом подтверждённом дубле.

## Связь с метриками

Мера должна снизить число дефектов в критичном потоке заказа и повысить долю успешных тестов после повторного прогона. Она также защищает SLI своевременной доступности и согласованности заказов из семинара 5.
