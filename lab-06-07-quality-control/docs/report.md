## 1. Отчёт о тестировании Sirius EDA

**Тип документа:** учебный отчёт о тестировании (модельный пример)  
**Система:** Sirius EDA — система заказа питания в столовой  
**Версия сборки:** 1.0.0-rc1 (условная)  
**Идентификатор исходной ревизии:** не задан; значения не подменяются SHA репозитория лабораторных  
**Дата модельного среза:** 26.11.2026

### 1. Резюме

**Решение по модельному набору: релиз не готов.**

В учебной модели предусмотрено 50 тестов, выполнено 47, успешно пройдено 44. Доля успешных среди выполненных — 93,62%. Три теста завершились неуспешно; один из них подробно описан в карточке BUG-001. Ещё три проверки не выполнены из-за отсутствия отдельного стенда для отказных сценариев RabbitMQ, нагрузочного испытания и восстановления PostgreSQL.

Основной модельный риск — рассогласование между фиксацией состояния заказа в PostgreSQL и публикацией события в RabbitMQ. При отказе брокера в критический момент заказ может остаться в промежуточном состоянии без запуска последующих обработчиков. Это сценарий для учебного документирования, а не утверждение о подтверждённом дефекте текущей сборки Sirius EDA.

### 2. Объект и область тестирования

В область рассмотрения входят:
- получение меню и просмотр доступных позиций;

- оплата заказа и публикация события `order_paid`;
- асинхронная обработка заказа кухней и доставкой;
- компенсационные действия Saga при ошибках;
- корректность хранения состояния заказа в PostgreSQL.

Проверки инфраструктуры внешних провайдеров находятся за пределами модели. Для асинхронных операций успешный HTTP-ответ не считается доказательством завершения всего процесса: дополнительно проверяются событие и конечное состояние заказа.

### 7. Риски

1. **Потеря события заказа (высокий риск).** При разрыве между фиксацией данных и публикацией события RabbitMQ последующие обработчики могут не получить работу.
2. **Задержка обработки (средний/высокий риск).** Очередь или worker могут отставать в пиковый период.
3. **Непроверенное восстановление (высокий риск).** T-050 не подтверждает фактическую возможность восстановить БД в заданных пределах.
4. **Повторная доставка события (средний риск).** При повторной доставке необходима идемпотентность обработчиков кухни, доставки и Saga.
5. **Неполнота измерений (средний риск).** Без единого идентификатора корреляции сложно связать HTTP-запрос, сообщение RabbitMQ и действие worker в один сценарий.

### 8. Заключение и условия выпуска

По модельным результатам релиз не рекомендуется к выпуску.

Положительное решение допускается после выполнения следующих условий:
- закрыт BUG-001: событие не теряется при отказе брокера либо состояние операции надёжно восстанавливается;
- повторная доставка `order_paid` не вызывает повторного списания или дублирования побочных эффектов;
- BUG-002 исправлен или принят владельцем продукта с документированным обоснованием;
- BUG-003 исправлен либо подтверждено, что отклонение не влияет на денежный расчёт;
- выполнены T-048, T-049 и T-050, сохранены журналы и результаты;
- пройдены все блокирующие сценарии создания, оплаты, обработки и компенсации заказа;
- доля успешных тестов достигает согласованного release gate 98%, а открытых Critical/Major дефектов в критичном потоке нет.

Перед реальным выпуском отчёт должен быть дополнен фактическим хешем сборки, конфигурацией стенда, ссылками на прогоны CI и доказательствами из журналов и базы данных.

## 3. Карточка дефекта BUG-001

| Поле | Значение |
|---|---|
| ID | BUG-001 |
| Заголовок | Событие `order_paid` может не попасть в RabbitMQ после фиксации состояния заказа |
| Система | Sirius EDA |
| Версия | 1.0.0-rc1, учебная модель |
| Компонент | API / PostgreSQL / публикация события RabbitMQ |
| Серьёзность | Major |
| Приоритет | P1 / High |
| Статус | Open (модельный дефект) |

### Описание

Сценарий моделирует отказ брокера в промежутке между фиксацией связанного с оплатой состояния заказа в PostgreSQL и публикацией события `order_paid`. Если событие не опубликовано и механизм повторной отправки не срабатывает, обработчики кухни и доставки не получают уведомление. Заказ может остаться в промежуточном состоянии, хотя API уже завершил часть операции.

**Важно:** это учебный сценарий, основанный на архитектурном риске отсутствия transactional outbox. Он не утверждает, что дефект воспроизведён на текущем стенде Sirius EDA.

### Предусловия

- Подготовлен тестовый пользователь с достаточным балансом.
- В меню есть доступная позиция.
- API, PostgreSQL и RabbitMQ доступны.
- Для наблюдения доступны состояние заказа и журналы API/брокера/worker.
- Тест выполняется только на изолированном стенде с тестовыми данными.

### Шаги воспроизведения

1. Авторизоваться тестовым пользователем.
2. Создать заказ через `POST /orders/create` с корректными `item_id` и `quantity`.
3. Инициировать оплату через `POST /orders/{order_id}/pay`.
4. В контролируемом тесте сделать RabbitMQ недоступным в момент публикации события `order_paid`, сохранив доступность PostgreSQL.
5. Проверить состояние заказа в PostgreSQL или через предусмотренный API просмотра заказа.
6. Проверить журналы API, RabbitMQ и обработчика кухни.
7. После восстановления RabbitMQ проверить, появилось ли событие и продолжилась ли обработка заказа.

### Ожидаемый результат

Система не теряет бизнес-событие при временной недоступности RabbitMQ. После восстановления брокера событие публикуется повторно либо операция восстанавливается из надёжно сохранённого состояния. Обработчики получают событие, а повторная доставка не приводит к дублированию побочных эффектов.

### Фактический результат в учебном сценарии

В модельном сценарии состояние операции уже зафиксировано в PostgreSQL, но событие не появляется в RabbitMQ. Обработчик кухни не получает задание, заказ остаётся в промежуточном состоянии до ручного вмешательства или отдельного механизма сверки.

### Серьёзность и приоритет

Severity Major: затрагивается критичный процесс обработки заказа и согласованность состояния между компонентами. Priority P1 / High: проблема требует устранения до релиза, поскольку может блокировать обработку принятых заказов. Временная ручная сверка не является надёжным обходным решением.

### Доказательства для реальной регистрации

- Временная шкала запроса оплаты и результата транзакции PostgreSQL.
- Журнал API с correlation_id и order_id.
- Журнал RabbitMQ или сведения о неподтверждённой публикации.
- Состояние очереди и отсутствие соответствующего события.
- Журнал worker, подтверждающий отсутствие обработки заказа.

Все токены, персональные данные и секреты перед приложением логов должны быть удалены или замаскированы.

### Критерий закрытия

После исправления:
1. при недоступности RabbitMQ событие остаётся в надёжном хранилище для последующей публикации;
2. после восстановления брокера обработчик получает событие;
3. повторная публикация не приводит к повторному списанию, созданию дублей или повторной компенсации;
4. интеграционный тест с отказом брокера проходит, а доказательства повторного прогона приложены к тикету.

### 3. Решение по инспекции

Замечания REV-001 и REV-002 следует устранить или принять владельцем системы с документированным обоснованием до релиза. REV-003 и REV-004 включить в план улучшений и проверить при интеграционном тестировании.

### 4. Контроль устранения

Каждое замечание должно быть связано с тикетом и pull request. После исправления инспектор проверяет изменение, а QA прикладывает результаты повторных тестов. Статус замечания меняется на закрытый только после подтверждения результата, а не после самого факта изменения документа или кода.

## 5. Показатели качества Sirius EDA

**Статус:** учебный расчёт на модельных исходных данных. Значения не являются результатами реального запуска тестов.

### Исходные данные

| Параметр | Значение | Примечание |
|---|---:|---|
| Учтённые дефекты для плотности | 25 | Модельный набор |
| Размер анализируемого кода | 12,5 KLOC | Условная оценка, требует замены на фактический размер |
| Пройденные тесты | 44 | Модельный прогон |
| Выполненные тесты | 47 | Не включает заблокированные |
| Проверенные требования | 38 | Модельный набор |
| Все требования | 40 | Модельный набор |
| Дефекты, найденные до выпуска | 18 | Условная выборка |
| Дефекты, найденные после выпуска | 2 | Условная выборка |
| Время устранения пяти дефектов | 1,5; 2; 2,5; 3; 4,5 ч | Модельные интервалы |

### Расчёт показателей

| Показатель | Формула | Расчёт | Значение | Интерпретация |
|---|---|---|---:|---|
| Плотность дефектов | D = Nдефектов / KLOC | 25 / 12,5 | 2,00 дефекта/KLOC | Требует одинаковых правил регистрации дефектов и подсчёта строк |
| Доля пройденных тестов | P = Nпройденных / Nвыполненных × 100% | 44 / 47 × 100% | 93,62% | Заблокированные и пропущенные тесты показываются отдельно |
| Покрытие требований | C = Nпроверенных / Nвсех требований × 100% | 38 / 40 × 100% | 95,00% | Наличие теста и успешное подтверждение требования следует учитывать раздельно |
| Эффективность обнаружения дефектов | E = Nдо / (Nдо + Nпосле) × 100% | 18 / (18 + 2) × 100% | 90,00% | Зависит от полноты учёта дефектов после выпуска |
| Среднее время устранения (MTTR) | MTTR = Σ(tзакрытия − tрегистрации) / n | (1,5 + 2 + 2,5 + 3 + 4,5) / 5 | 2,70 ч | Среднее дополняется медианой, p90 и числом незакрытых дефектов |

### Правила интерпретации

- Для доли пройденных тестов знаменатель — только фактически выполненные тесты. Заблокированные проверки нельзя записывать как успешные.
- Покрытие требований не гарантирует глубину тестирования. Связь требования с тестом и успешный результат должны фиксироваться отдельно.
- Плотность дефектов имеет смысл только при одинаковой методике подсчёта дефектов и размера кода.
- Эффективность обнаружения зависит от выбранного окна наблюдения после релиза и полноты регистрации дефектов.
- MTTR в этой работе означает среднее время от регистрации дефекта до закрытия. Незакрытые дефекты дополнительно показываются отдельно, чтобы среднее не создавало ложного впечатления улучшения.

### Вывод

В модельном наборе доля успешных тестов 93,62% ниже учебного release gate 98%, а покрытие требований 95% оставляет две непроверенные области. Эффективность обнаружения 90% и MTTR 2,70 часа не отменяют блокирующего риска BUG-001. Поэтому по совокупности критериев учебный релиз не рекомендуется к выпуску. Для фактического заключения все входные значения необходимо заменить выгрузками CI, трекера и журналов Sirius EDA.

<a id="section-6"></a>
## 6. Рекомендация по улучшению качества Sirius EDA

### Проблема и доказательство

В модельной карточке BUG-001 описан риск потери события `order_paid` при отказе RabbitMQ после фиксации состояния операции в PostgreSQL. Это может остановить асинхронную обработку заказа кухней и доставкой. Архитектурный контекст также требует учитывать повторную доставку событий и идемпотентность обработчиков.

Сценарий является учебным и должен быть подтверждён fault-injection тестом на изолированном стенде до регистрации как фактического дефекта.

### Корректирующее действие

Рассмотреть transactional outbox для публикации бизнес-событий:
- сохранять изменение состояния заказа и запись о событии в одной транзакции PostgreSQL;
- отдельному publisher-процессу выбирать неподтверждённые события и публиковать их в RabbitMQ;
- помечать событие опубликованным только после подтверждения брокера;
- предусмотреть повторные попытки с backoff и мониторинг возраста самой старой необработанной записи;
- обеспечить идемпотентность потребителей по идентификатору события/заказа.

Такой подход устраняет разрыв между фиксацией данных и отправкой события. Он не отменяет необходимость идемпотентности: RabbitMQ и publisher могут доставить одно событие повторно.

### Предупреждающее действие

Включить в архитектурный чек-лист для новых асинхронных сценариев:
- определение владельца события и схемы его версии;
- описание гарантии доставки и стратегии повторов;
- идемпотентную обработку на стороне consumer;
- dead-letter queue для некорректных/необрабатываемых сообщений;
- корреляцию HTTP-запроса, сообщения и действий worker;
- тесты отказа брокера и повторной доставки.

### План выполнения

| Поле | Значение |
|---|---|
| Ответственный | Backend team lead |
| Исполнители | Backend-разработчик, инженер сопровождения и QA |
| Срок | 7 календарных дней после утверждения (учебный срок) |
| Приоритет | P1 / High |
| Результат | Согласованная схема надёжной публикации событий, тесты отказа и повторной доставки, метрики очереди |

### Проверка эффективности

1. Выполнить заказ и инициировать оплату при штатно работающем RabbitMQ.
2. Повторить сценарий, временно остановив брокер до публикации события.
3. Убедиться, что событие сохранено в outbox и не потеряно.
4. Восстановить брокер и проверить доставку события обработчику.
5. Повторно доставить одно событие и подтвердить отсутствие повторного списания/побочного эффекта.
6. Проверить dead-letter сценарий и возможность повторной обработки после устранения причины.
7. Сопоставить журналы API, publisher, RabbitMQ и worker по correlation_id и идентификатору события.

**Критерии успеха:** 100% тестовых событий после восстановления брокера доставляются или явно переводятся в контролируемое состояние ошибки; дубли не создают повторных бизнес-эффектов; возраст необработанных событий остаётся в согласованном SLO.

### Контроль выполнения

Задача закрывается после ссылки на merged pull request, результатов повторного прогона, логов и подтверждения эффективности. Одного факта внесения изменения недостаточно.
