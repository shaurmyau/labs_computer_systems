# Карточка дефекта BUG-001

| Поле | Значение |
|---|---|
| ID | BUG-001 |
| Заголовок | Повторный POST /api/orders после timeout создаёт дублирующий заказ для одного клиента |
| Система | OrderFlow |
| Версия | 1.0.0-rc1, учебная модель |
| Окружение | Изолированный staging, Ubuntu Server 22.04 |
| Браузер / клиент | Chromium на Linux; повтор запроса также воспроизводится API-клиентом |
| Серьёзность | Major |
| Приоритет | P1 / High |
| Статус | Open |
| Компонент | Order API / сохранение заказа |

## Предусловия

- Пользователь авторизован.
- В каталоге существует активный товар product_id=7.
- Для пользователя подготовлена тестовая корзина.
- Сервис принимает POST /api/orders.

## Шаги воспроизведения

1. Авторизоваться тестовым пользователем с customer_id=42.
2. Отправить POST /api/orders с телом {"customer_id":42,"items":[{"product_id":7,"qty":1}]}.
3. Искусственно оборвать ожидание ответа клиента после отправки запроса, не отменяя обработку на сервере.
4. Повторно отправить тот же POST с тем же содержимым.
5. Выполнить GET /api/orders?customer_id=42.
6. Сравнить количество созданных заказов и их состав.

## Ожидаемый результат

Повторная отправка одного и того же пользовательского действия не должна создавать новый заказ. API должен вернуть результат уже принятой операции или безопасно сообщить о конфликте. В базе должен существовать один заказ для одного идемпотентного ключа.

## Фактический результат в учебном сценарии

В модельном сценарии создаются два разных order_id с одинаковым набором customer_id и items. Оператору приходится выявлять дубликат и отменять лишний заказ вручную.

## Обоснование серьёзности и приоритета

Серьёзность Major: дефект затрагивает целостность бизнес-операции, создаёт повторную обработку и может привести к двойному резервированию или списанию. Приоритет P1 / High назначен из-за критичности создания заказа и отсутствия безопасного автоматического обхода. Временный обходной путь — ручная проверка дубликатов оператором — дорогой, не масштабируется и не гарантирует предотвращение повторного платежа.

## Возможные вложения для реального наблюдения

- HAR-файл или экспорт запросов API с замаскированными токенами.
- Лог API с correlation_id, двумя order_id и временными метками.
- Результат SQL-запроса, подтверждающий две записи.
- Короткая запись экрана с последовательностью повторной отправки.

Пример формата диагностической записи (иллюстративный, не реальный лог):

~~~text
2026-11-23T10:15:02Z POST /api/orders customer_id=42 request_id=demo-001 -> 201 order_id=OF-1001
2026-11-23T10:15:04Z POST /api/orders customer_id=42 request_id=demo-001 -> 201 order_id=OF-1002
2026-11-23T10:15:05Z GET /api/orders?customer_id=42 -> [OF-1001, OF-1002]
~~~

## Критерий закрытия

После исправления повтор POST с тем же Idempotency-Key должен возвращать тот же order_id; в БД должна действовать уникальность ключа в области клиента. Интеграционный тест повторяет запрос не менее двух раз и проверяет, что количество записей равно одному.
